# FNR-1: Концепты решений

## Проблема

Шаг релиза считается успешным сразу после прохождения проверок (`delivery_verify`) в `workflow.py:234-239`. Если проверки зелёные, шаг помечается как выполненный, даже если сервис упадёт через несколько секунд после этого. Отсутствует окно наблюдения за состоянием контейнера после выкатки.

## Зона воздействия

| Файл | Роль | Изменения |
|------|-----|-----------|
| `poh_delivery/workflow.py:213-252` | Воркфлоу | Внедрение окна наблюдения между `deploy` и `verify` |
| `poh_delivery/model.py:124-133` | Модель | Новые поля в `StepOutcome` для результатов наблюдения |
| `poh_delivery/prod.py:95-148` | Прод-контур | Метод наблюдения за состоянием контейнера |
| `poh_delivery/ports.py:32-38` | Протокол | Новый метод в `ProdPort` |
| `poh_delivery/activities.py:142-157` | Активности | Новая активность `delivery_observe` |
| `poh_delivery/render.py:146-205` | Отчёты | Раздел о наблюдении в релизе |
| `tests/test_workflow.py:209` | Тесты | Проверка порядка шагов с окном |

## Концепт 1: Правильное — Полноценное окно наблюдения с Docker health-check

### Суть

Внедрить окно наблюдения как отдельный шаг воркфлоу с периодической проверкой состояния контейнера через Docker API. Контейнер проверяется на:
- Статус (`running` vs `exited`)
- Restart count (через `docker inspect`)
- PID-стабильность (одинаков ли PID контейнера между проверками)

Финальные проверки запускаются только после успешного прохождения окна.

### Изменяемые файлы

| Файл | Конкретные изменения |
|------|---------------------|
| `model.py` | Новый dataclass `ObservationResult(duration: int, alive: bool, restarts: int, detail: str)`. Поля в `StepOutcome`: `observation: ObservationResult | None` |
| `ports.py` | Метод в `ProdPort`: `def observe(self, duration: int, service: dict) -> ObservationResult` |
| `prod.py` | Реализация `observe()` в `DockerProd` с использованием `docker inspect` каждые 10 секунд |
| `activities.py` | Активность `@activity.defn(name="delivery_observe")` |
| `workflow.py:252` | Внедрение: `deployed = await deploy(...); observed = await observe(...); checks = await verify(...)` |
| `render.py` | Блок "Наблюдение после выкатки" в `report_md()` |
| `tests/test_workflow.py` | `assert window[:5] == [..., "observe", "verify"]` |

### Плюсы

- Проверяет все критерии жизнеспособности: статус, перезапуски, PID-стабильность
- Отдельная активность = отдельное событие в истории Temporal для разбора инцидентов
- Настраиваемая длительность через переменную окружения
- Нулевая длительность = режим отладки (без окна)

### Минусы

- Увеличивает время каждого шага на длительность окна (по умолчанию 120с)
- Требует изменений в 7 файлах
- Периодические `docker inspect` могут нагружать демон при большом числе релизов

### Усилия

**3-4 дня** (изменения в 7 файлах + тесты + документация)

### Риски

- **Средний:** Docker API может не отдавать restart count без дополнительных вызовов
- **Низкий:** Увеличение времени релиза может раздражать при частых выкатках

## Концепт 2: Прагматичное — Множественные финальные проверки

### Суть

Вместо наблюдения за контейнером запускать финальные проверки **трижды** с интервалом 60 секунд. Если все три прогона зелёные — сервис стабилен. Это использует существующий механизм (`verify`) без добавления нового наблюдения.

### Изменяемые файлы

| Файл | Конкретные изменения |
|------|---------------------|
| `workflow.py:252` | После `verify` → цикл 2× ещё раз с `workflow.sleep(60)` между |
| `model.py` | Поле `verification_runs: int` в `StepOutcome` (сколько раз прогнали проверки) |
| `render.py` | Строка "Прогонов финальных проверок: N" в отчёте |

### Плюсы

- Минимальные изменения (2-3 файла)
- Использует существующий механизм без Docker API
- Три прогона = естественный фильтр на флактивающее поведение
- Интервал 60с = достаточное окно для проявления проблем памяти/потоков

### Минусы

- Не обнаруживает перезапуск контейнера, если он происходит между проверками
- Не даёт точного времени провала (когда именно упал)
- Увеличивает время шага на 120с фиксированно (не настраивается)

### Усилия

**1-2 дня** (изменения в 2-3 файлах + базовые тесты)

### Риски

- **Низкий:** Сервис может отвечать 200, но быть в процессе краша (OOM в процессе)
- **Низкий:** Фиксированный интервал может быть слишком длинным или коротким

## Концепт 3: Быстрый костыль — Переменная окружения с `sleep`

### Суть

Добавить переменную окружения `DELIVERY_OBSERVE_SECONDS` и `sleep` в воркфлоу между `deploy` и `verify`. Никаких проверок состояния контейнера — просто пауза. Нулевое значение = прежнее поведение.

### Изменяемые файлы

| Файл | Конкретные изменения |
|------|---------------------|
| `workflow.py:252` | После `deploy` → `sleep(int(os.environ.get("DELIVERY_OBSERVE_SECONDS", "0")))` |
| `model.py` | Поле `observation_seconds: int` в `StepOutcome` |
| `render.py` | Строка "Окно наблюдения: N сек" в отчёте |

### Плюсы

- **Минимальные изменения** (1 файл основной, 2 на модель/рендер)
- Работает немедленно после выката самого агента
- Ноль = режим отладки без изменений поведения
- Даёт времени для проявления проблем без сложной логики

### Минусы

- Не проверяет жив ли контейнер — просто пауза
- Сервис может быть мёртв всё окно, и `verify` обнаружит это только в конце
- Никакой диагностики —只知道 что прошло время

### Усилия

**4-6 часов** (1-2 файла + базовый тест)

### Риски

- **Низкий:** Ложное чувство безопасности — пауза ≠ проверка
- **Низкий:** Увеличение времени релиза без гарантий

## Концепт 4: Креативный хак — Docker health-check + Graceful shutdown

### Суть

Использовать механизм Docker `--health-cmd` для встроенного наблюдения. При выкатке передавать `--health-cmd` с проверкой health_path, а во время окна опрашивать статус health-check через `docker inspect`. Финальные проверки запускаются только при `healthy` статусе.

### Изменяемые файлы

| Файл | Конкретные изменения |
|------|---------------------|
| `prod.py` | В `deploy()` добавить `--health-cmd` и `--health-interval` в `docker run`. Метод `observe()` опрашивает `Health.Status` через `docker inspect` |
| `ports.py` | Метод `def observe(self, duration: int) -> ObservationResult` |
| `activities.py` | Активность `delivery_observe` |
| `workflow.py` | Внедрение окна с вызовом `observe` |
| `model.py` | `ObservationResult` с полями `healthy: bool, health_status: str` |

### Плюсы

- Использует встроенный механизм Docker для health-check
- Статус health-check виден в `docker ps` и других инструментах
- Docker сам управляет интервалом и таймаутами
- Менее нагружает демон (опрос только статуса, не полный inspect)

### Минусы

- Требует изменения команды `docker run` — может сломать существующие инсталляции
- Health-check может давать ложные срабатывания при сетевых задержках
- Более сложная конфигурация (интервал, таймаут, retries)

### Усилия

**2-3 дня** (изменения в 5 файлах + тесты + документация)

### Риски

- **Средний:** Health-check требует времени на стабилизацию (initial delay)
- **Средний:** Сетевые проблемы внутри контейнера могут быть ошибочно приняты за краш сервиса

## Концепт 5: «Не трогай» — Отложить до сбора метрик

### Суть

Не внедрять окно наблюдения сейчас. Дождаться первого инцидента и собрать метрики:
- Время до краша после выкатки
- Типы сбоев (OOM, restart, exception)
- Частота проблем

Тогда внедрять решение на реальных данных.

### Изменяемые файлы

Нет изменений. Добавляется Issue в репозиторий для сбора статистики.

### Плюсы

- Нет риска внести регрессию
- Решение будет основано на реальных данных, не на гипотезах
- Экономия времени разработчиков

### Минусы

- Первый инцидент может быть болезненным для прод-контура
- Откладывает решение проблемы на неопределённый срок
- Нет данных до первого провала

### Усилия

**1 день** (создание Issue для сбора метрик)

### Риски

- **Высокий:** Инцидент может произойти в критический момент
- **Средний:** Отсутствие данных мешает приоритизации задачи

## Ответы на открытые вопросы из task.md

1. **Периодичность проверки:** Концепт 1 — каждые 10 секунд (настраиваемо); Концепт 2 — 3 прогона с интервалом 60с
2. **Хранение в StepOutcome:** Концепт 1 — отдельный dataclass `ObservationResult`; Концепт 2 — просто счётчик прогонов
3. **Настройка длительности:** Переменная окружения `DELIVERY_OBSERVE_SECONDS` (как `DELIVERY_READY_TIMEOUT`)
4. **Формулировка причины:** "Контейнер остановился на секунде X окна" или "Финальная проверка healthz вернула 500"
