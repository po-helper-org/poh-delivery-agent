## 1. Резюме проблемы

В репозитории `poh-delivery-agent` отсутствует workflow для автоматического запуска PR-Agent при открытии PR. Это приводит к блокировке релизов из-за отсутствия вердикта ревью (`REVIEW_PENDING` → `NONE`).

**Зона воздействия:**
- `.github/workflows/` — единственное место для изменений (по ограничению ОГР-1)
- `poh_delivery/review.py` — уже готов принимать вердикт (изменения не требуются)
- `poh_delivery/rules.py` — уже классифицирует по вердикту (изменения не требуются)

**Ограничения:**
- Не трогать код Delivery-Agent
- Использовать механизм из демо `poh-demo-checkout`
- Права токена GitHub App на workflows

## 2. Концепты решений

### Концепт A: Правильное — Полноценный GitHub Actions workflow ⭐

**Суть:** Добавить `.github/workflows/pr-review.yml` по образцу демо-репозитория с полной интеграцией в GitHub Actions.

**Детали:**
- Триггеры: `pull_request:opened`, `issue_comment` (команда `/review`)
- Использование CLI-образа pr-agent через Docker
- Автоматический комментарий с коммитом «review updated until ...»
- Опциональная отправка события в Issue Agent (если секреты настроены)
- Обработка rate-limit с паузой 90 секунд

**Изменяемые файлы:**
- `.github/workflows/pr-review.yml` (новый файл)

**Плюсы:**
- ✅ Полное покрытие функциональных требований (ТР-1, ТР-2, ТР-3, ТР-4, ТР-5, ТР-6)
- ✅ Соответствие ограничению ОГР-2 (механизм из демо)
- ✅ Не требует изменений кода Delivery-Agent
- ✅ Масштабируемое решение для будущих расширений
- ✅ Прозрачное для разработчиков решение (стандарт GitHub Actions)

**Минусы:**
- ⚠️ Требует права `workflows` у GitHub App
- ⚠️ Зависимость от доступности Docker Hub
- ⚠️ Требует настройки секретов (`LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL`)

**Усилия:** 2-4 часа

**Риски:**
- Средний: отсутствие прав на workflows (проверяем до начала)
- Низкий: rate-limit LLM API (есть retry)

### 😈 Адвокат Дьявола: Атака на Концепт A

Давай посмотрим, что **может пойти не так**:

1. **Права на workflows — риск блокировки**
   - Что если у GitHub App НЕТ прав на `workflows`?
   - Пуш упадёт, PR #19 останется заблокированным
   - Ты даже не сможешь добавить файл через API
   - Вывод: весь КОНЦЕПТ А ставится на карту предположения, которое может быть ложным

2. **Зависимость от Docker Hub**
   - pr-agent запускается через Docker-образ
   - Что если Docker Hub недоступен (rate-limit, outage)?
   - Критический путь: PR → review → релиз
   - Сбой Docker Hub = заблокированные релизы

3. **Секреты не настроены**
   - ОВ-2: `LLM_API_KEY`, `LLM_MODEL`, `LLM_BASE_URL` могут отсутствовать
   - Workflow упадёт на первом же запуске
   - Отладка в GitHub Actions — боль (логи, retry, таймауты)

4. **Вопрос интеграции с Issue Agent**
   - Концепт A включает опциональную отправку события в Issue Agent
   - Зачем это нужно, если круг правок уже читает ревью?
   - Лишняя сложность → лишние точки отказа

5. **20 минут — долго**
   - НТР-1: ≤ 20 минут timeout
   - Разработчик ждёт ревью → делает правку → ждёт снова
   - Цикл может растянуться на час+

**Мой приговор:** Концепт A — good enough, но есть скрытые риски, которые могут заблокировать задачу.

## Раунд 2: Пересмотр

### 🏛️ Архитектор: Ответ на критику

Отвечаю по пунктам:

1. **Права на workflows** — это не риск, это **предусловие**:
   - Добавил ОВ-1 в "Следующие шаги" в concept.md
   - Если прав нет → человек добавит файл вручную
   - Workflow всё равно заработает при триггере
   - **Митигация:** Проверка прав до начала — 5 минут, не 2-4 часа

2. **Docker Hub недоступен** — есть стандартные митигации:
   - GitHub Actions кэширует Docker-слои
   - Rate-limit на Docker Hub можно обойти через токен
   - В худшем случае — redeploy workflow с альтернативным registry
   - **Это не критический путь**, workflow можно быстро починить

3. **Секреты не настроены** — верно, но:
   - Это проверяется в ОВ-2 (в concept.md, строка 219)
   - Если секретов нет → workflow упадёт с понятной ошибкой
   - Добавить секрет = 2 минуты
   - **Не критично**, не требует изменений в коде

4. **Интеграция с Issue Agent** — опционально:
   - Слово "опциональная" есть в описании (строка 35)
   - Можно не добавлять этот блок
   - Концепт B вообще без него — оба концепта покрывают ТР-1 через ТР-4

5. **20 минут — это верхняя граница**
   - Обычно ревью занимает 3-5 минут
   - 20 минут — timeout на случай rate-limit
   - Если критично → можно снизить до 10 минут
   - **Но это не решает проблему блокировки PR**

**Усиление позиции:** Концепт A остаётся оптимальным, но я признаю:
- Нужно проверить права и секреты **до** написания workflow
- Интеграцию с Issue Agent можно сделать опциональной или убрать
- Можно добавить fallback-сценарий при недоступности Docker Hub
