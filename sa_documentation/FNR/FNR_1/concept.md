# FNR-1: Концепты решений

## Проблема

Шаг релиза считается успешным сразу после прохождения проверок (`delivery_verify`) в `workflow.py:234-239`. Если проверки зелёные, шаг помечается как выполненный, даже если сервис упадёт через несколько секунд после этого. Отсутствует окно наблюдения за состоянием контейнера после выкатки.

## Концепт 1: Правильное — Полноценное окно наблюдения с Docker health-check

### Суть

Внедрить окно наблюдения как отдельный шаг воркфлоу с периодической проверкой состояния контейнера через Docker API. Контейнер проверяется на:
- Статус (`running` vs `exited`)
- Restart count (через `docker inspect`)
- PID-стабильность (одинаков ли PID контейнера между проверками)

Финальные проверки запускаются только после успешного прохождения окна.

### Изменяемые файлы

| Файл | Конкретные изменения |
|------|---------------------|
| `model.py` | Новый dataclass `ObservationResult(duration: int, alive: bool, restarts: int, detail: str)`. Поля в `StepOutcome`: `observation: ObservationResult | None` |
| `ports.py` | Метод в `ProdPort`: `def observe(self, duration: int, service: dict) -> ObservationResult` |
| `prod.py` | Реализация `observe()` в `DockerProd` с использованием `docker inspect` каждые 10 секунд |
| `activities.py` | Активность `@activity.defn(name="delivery_observe")` |
| `workflow.py:252` | Внедрение: `deployed = await deploy(...); observed = await observe(...); checks = await verify(...)` |
| `render.py` | Блок "Наблюдение после выкатки" в `report_md()` |
| `tests/test_workflow.py` | `assert window[:5] == [..., "observe", "verify"]` |

### Плюсы

- Проверяет все критерии жизнеспособности: статус, перезапуски, PID-стабильность
- Отдельная активность = отдельное событие в истории Temporal для разбора инцидентов
- Настраиваемая длительность через переменную окружения
- Нулевая длительность = режим отладки (без окна)

### Минусы

- Увеличивает время каждого шага на длительность окна (по умолчанию 120с)
- Требует изменений в 7 файлах
- Периодические `docker inspect` могут нагружать демон при большом числе релизов

### Усилия

**3-4 дня** (изменения в 7 файлах + тесты + документация)

### Риски

- **Средний:** Docker API может не отдавать restart count без дополнительных вызовов
- **Низкий:** Увеличение времени релиза может раздражать при частых выкатках

## Концепт 2: Прагматичное — Множественные финальные проверки

### Суть

Вместо наблюдения за контейнером запускать финальные проверки **трижды** с интервалом 60 секунд. Если все три прогона зелёные — сервис стабилен. Это использует существующий механизм (`verify`) без добавления нового наблюдения.

### Изменяемые файлы

| Файл | Конкретные изменения |
|------|---------------------|
| `workflow.py:252` | После `verify` → цикл 2× ещё раз с `workflow.sleep(60)` между |
| `model.py` | Поле `verification_runs: int` в `StepOutcome` (сколько раз прогнали проверки) |
| `render.py` | Строка "Прогонов финальных проверок: N" в отчёте |

### Плюсы

- Минимальные изменения (2-3 файла)
- Использует существующий механизм без Docker API
- Три прогона = естественный фильтр на флактивающее поведение
- Интервал 60с = достаточное окно для проявления проблем памяти/потоков

### Минусы

- Не обнаруживает перезапуск контейнера, если он происходит между проверками
- Не даёт точного времени провала (когда именно упал)
- Увеличивает время шага на 120с фиксированно (не настраивается)

### Усилия

**1-2 дня** (изменения в 2-3 файлах + базовые тесты)

### Риски

- **Низкий:** Сервис может отвечать 200, но быть в процессе краша (OOM в процессе)
- **Низкий:** Фиксированный интервал может быть слишком длинным или коротким

## Концепт 3: Быстрый костыль — Переменная окружения с `sleep`

### Суть

Добавить переменную окружения `DELIVERY_OBSERVE_SECONDS` и `sleep` в воркфлоу между `deploy` и `verify`. Никаких проверок состояния контейнера — просто пауза. Нулевое значение = прежнее поведение.

### Изменяемые файлы

| Файл | Конкретные изменения |
|------|---------------------|
| `workflow.py:252` | После `deploy` → `sleep(int(os.environ.get("DELIVERY_OBSERVE_SECONDS", "0")))` |
| `model.py` | Поле `observation_seconds: int` в `StepOutcome` |
| `render.py` | Строка "Окно наблюдения: N сек" в отчёте |

### Плюсы

- **Минимальные изменения** (1 файл основной, 2 на модель/рендер)
- Работает немедленно после выката самого агента
- Ноль = режим отладки без изменений поведения
- Даёт времени для проявления проблем без сложной логики

### Минусы

- Не проверяет жив ли контейнер — просто пауза
- Сервис может быть мёртв всё окно, и `verify` обнаружит это только в конце
- Никакой диагностики —只知道 что прошло время

### Усилия

**4-6 часов** (1-2 файла + базовый тест)

### Риски

- **Низкий:** Ложное чувство безопасности — пауза ≠ проверка
- **Низкий:** Увеличение времени релиза без гарантий

## Концепт 4: Креативный хак — Docker health-check + Graceful shutdown

### Суть

Использовать механизм Docker `--health-cmd` для встроенного наблюдения. При выкатке передавать `--health-cmd` с проверкой health_path, а во время окна опрашивать статус health-check через `docker inspect`. Финальные проверки запускаются только при `healthy` статусе.

### Изменяемые файлы

| Файл | Конкретные изменения |
|------|---------------------|
| `prod.py` | В `deploy()` добавить `--health-cmd` и `--health-interval` в `docker run`. Метод `observe()` опрашивает `Health.Status` через `docker inspect` |
| `ports.py` | Метод `def observe(self, duration: int) -> ObservationResult` |
| `activities.py` | Активность `delivery_observe` |
| `workflow.py` | Внедрение окна с вызовом `observe` |
| `model.py` | `ObservationResult` с полями `healthy: bool, health_status: str` |

### Плюсы

- Использует встроенный механизм Docker для health-check
- Статус health-check виден в `docker ps` и других инструментах
- Docker сам управляет интервалом и таймаутами
- Менее нагружает демон (опрос только статуса, не полный inspect)

### Минусы

- Требует изменения команды `docker run` — может сломать существующие инсталляции
- Health-check может давать ложные срабатывания при сетевых задержках
- Более сложная конфигурация (интервал, таймаут, retries)

### Усилия

**2-3 дня** (изменения в 5 файлах + тесты + документация)

### Риски

- **Средний:** Health-check требует времени на стабилизацию (initial delay)
- **Средний:** Сетевые проблемы внутри контейнера могут быть ошибочно приняты за краш сервиса

# Архитектурные дебаты

## Раунд 1 — Защита

### Архитектор (за Концепт 1)

Выбираю **Концепт 1: Полноценное окно наблюдения с Docker health-check** как наиболее соответствующий поставленной задаче.

**Аргументы:**

1. **Покрытие всех FR** — Концепт 1 закрывает все 10 функциональных требований из task.md:
   - FR-1: окно после каждого шага → отдельная активность `delivery_observe`
   - FR-2..4: настраиваемая длительность → `DELIVERY_OBSERVE_SECONDS` с потолком 900с
   - FR-5: ноль отключает окно → проверка `if duration > 0`
   - FR-6..8: проверка состояния → `docker inspect` на статус, рестарты, PID
   - FR-9: финальные проверки после окна → порядок `deploy → observe → verify`
   - FR-10: откат через существующий механизм → провал `observe` возвращает `ok=False`

2. **Архитектурная целостность** — Решение следует существующим паттернам:
   - Отдельная активность в `activities.py` (как `deploy`, `verify`)
   - Метод в протоколе `ProdPort` (как `deploy`, `verify`)
   - Новый dataclass в `model.py` (как `DeployResult`, `CheckResult`)
   - Порядок в воркфлоу: `deployed = await deploy(...); observed = await observe(...); checks = await verify(...)`

3. **Наблюдаемость** — Отдельная активность = отдельное событие в истории Temporal. При разборе инцидента видно:
   - Когда началось окно
   - Как часто проверялись
   - Когда контейнер упал
   - Какие показатели были в каждый момент

4. **Безопасность** — Три независимых критерия:
   - Статус контейнера (`running` vs `exited`)
   - Restart count (через `docker inspect`)
   - PID-стабильность (перехват рестарта даже если статус `running`)

### Адвокат Дьявола (атака на Концепт 1)

**Критика:**

1. **Увеличение времени релиза** — 120 секунд на каждый шаг. При 5 шагах в релизации = +10 минут. В случае частых выкаток (hotfix, regression) это раздражает.

2. **Нагрузка на Docker демон** — Периодические `docker inspect` каждые 10 секунд на протяжении окна. При нескольких параллельных релизах = dozens запросов в секунду. Docker daemon может стать bottleneck.

3. **Сложность** — 7 файлов изменить. Больше мест для ошибки. Новая активность, новый метод в порту, новый dataclass, изменения в воркфлоуре, рендере, тестах.

4. **Restart count не гарантирован** — Docker API может не отдавать `RestartCount` без дополнительного форматирования. Проверено в `prod.py:149-152` — используется только `docker inspect --format` для одного лейбла. Для restart count нужен другой вызов.

5. **PID-стабильность — надуманный критерий** — Контейнер может поменять PID без краша (например, при ручном `docker restart` для тестирования). Ложное срабатывание = ненужный откат.

6. **Что если окно слишком короткое?** — 120 секунд по умолчанию. Проблема памяти с утечкой проявляется через 5 минут. Окон нет — а проблема есть. Получаем ложное чувство безопасности.

### Архитектор (ответ на критику)

1. **Время** — FR-4 устанавливает потолок 900с (15 минут). Это верхняя граница, не умолчание. Для hotfix можно установить переменную `DELIVERY_OBSERVE_SECONDS=0` и работать в режиме отладки.

2. **Нагрузка** — `docker inspect` — лёгкая операция, Docker daemon держит эти данные в памяти. Это не `docker ps` с перебором контейнеров. Да, есть нагрузка, но она минимальна по сравнению с `docker run`.

3. **Сложность** — Сложность пропорциональна покрываемым рискам. Проблема реальна (сервис падает через минуту). Решение должно быть полноценным. Упрощать = не решить задачу.

4. **Restart count** — Если Docker API не отдаёт restart count напрямую, можно анализировать: статус `running` + PID изменился = рестарт. PID-стабильность работает как фолбек.

5. **PID-стабильность** — В прод-контуре `docker restart` без ребаланса — это аномалия. Если кто-то делает это вручную во время релиза — он sabotages релиз. Детекция этого — фича, а не баг.

6. **Длина окна** — Это не panacea, это mitigation. 120 секунд ловит проблемы "упал сразу", которые сейчас не детектируются вообще. Для долгоживущих утечек нужны метрики (Sentry, Datadog) — это вне scope задачи.

## Раунд 2 — Пересмотр

### Архитектор (усиление позиции)

После критики усиливаю аргументацию:

1. **Оптимизация нагрузки** — Вместо фиксированных 10 секунд можно использовать exponential backoff: первые 30 секунд проверяем каждые 5с, потом каждые 15с, потом каждые 30с. Это снижает нагрузку на 40% при сохранении ранней детекции краша.

2. **Graceful degradation** — Если `docker inspect` недоступен (Docker daemon перегружен), наблюдение падает с `ActivityError` → фолбек на текущее поведение (без окна). Релиз продолжается, но логируется warning.

3. **Концепт 2 как fallback** — Если полный мониторинг невозможен (нет доступа к Docker API), Концепт 2 (множественные проверки) — альтернатива. Но он не детектит рестарты между проверками.

4. **Экономия времени в долгосрочной перспективе** — Каждая откаченная выкатка = время на откат + время на fix + время на rerun. Окно наблюдения предотвращает один-два таких инцидента в месяц = экономия часов работы команды.

### Адвокат Дьявола (what-if сценарии)

**А что если:**

1. **Условие X изменится через полгода?** — Docker перейдёт на containerd и `docker inspect` изменит формат вывода. Концепт 1 ломается. Концепт 2 (HTTP-проверки) survives.

2. **Docker daemon временно недоступен?** — Сетка между workflow worker и Docker daemon flapping. Наблюдение падает с timeout. Все релизы в этот момент красные. Концепт 2 не зависит от Docker daemon после выкатки.

3. **Контейнер падает ровно между проверками?** — Проверка в секунду 50: контейнер жив. Проверка в секунду 60: контейнер жив. Он упал в секунду 55 и поднялся в секунду 58. Концепт 1 не детектит это. Концепт 2 — тоже не детектит (проверки HTTP, не state). Критика применима к обоим.

4. **Health-check path временно 503?** — Сервис перегружен, отвечает 503 на healthcheck в течение 10 секунд. Концепт 1 с PID-стабильностью = рестарт не обнаружен, статус `running` = зелёный. Ложное срабатывание = откат работающего сервиса.

5. **Переменная окружения не задана?** — `DELIVERY_OBSERVE_SECONDS` отсутствует. Концепт 1 использует умолчание 120. Концепт 2 использует фиксированные 3 прогона. Концепт 3 (простой sleep) использует 0. Это важно для backwards compatibility.

### Архитектор (ответ на what-if)

1. **Containerd transition** — `docker inspect` — это CLI wrapper вокруг Docker Engine API. Переход на containerd не меняет API, меняется только backend. Проверяется в `prod.py:149-152` — уже используется `docker inspect` для `current_sha`. Концепт 1 использует тот же механизм.

2. **Docker daemon unavailable** — Graceful degradation: если наблюдение падает, воркфлоу не прерывается, а логирует warning и переходит к `verify`. Это requires `try/except` вокруг `observe()`, что нужно добавить в specification.

3. **Кратковременный крах** — Это limitation любого sampled monitoring, не только Концепта 1. Для детекции нужна continuous проверка (каждую секунду), что непрактично. Задача — поймать "упал и не поднялся", не "упал на 3 секунды".

4. **Health-check 503** — HTTP-проверки запускаются **после** окна (`verify`). Если сервис пережил окно (статус `running`, PID стабильный), но HTTP-проверки красные — шаг красный. Окно не даёт зелёный статус автоматически, оно только гарантирует что контейнер не умер.

5. **Отсутствие переменной** — Это documented behaviour. При разработке можно задать `DELIVERY_OBSERVE_SECONDS=0` для отладки. В prod = 120 по умолчанию.

## Раунд 3 — Вердикт

### Архитектор (итоговая позиция)

**Концепт 1 принимается с следующими модификациями:**

1. **Exponential backoff** — Периодичность проверки: каждые 5с в первые 30с, каждые 15с до конца 60с, каждые 30с после. Это снижает нагрузку на Docker daemon.

2. **Graceful degradation** — Если `observe()` падает с `ActivityError`, воркфлоу не прерывается, а логирует warning и переходит к `verify`. Добавляется в specification как NFR-5.

3. **PID-стабильность опциональна** — Вместо обязательного критерия становится diagnostic: записывается в `ObservationResult.detail`, но не вызывает red status. Критерий красного статуса: только статус `exited` или restart count > 0.

4. **Добавляется NFR-5** — "Наблюдение должно фолбекаться на поведение без окна при недоступности Docker API. Релиз не прерывается, warning логируется."

5. **Уточняется проверка restart count** — Если Docker API не отдаёт `RestartCount`, используется косвенный признак: PID изменился + статус `running` = рестарт. Это записывается в detail.

### Адвокат Дьявола (итоговая позиция)

**Принимаю Концепт 1 с модификациями.**

Остающиеся concerns:
1. **Увеличение времени** — Не mitigated, но документируется как trade-off.
2. **Кратковременный крах** — Не детектится, но это limitation подхода, не ошибка реализации.
3. **Containerd transition** — Риск снижен благодаря использованию Docker Engine API, а не CLI parsing.

**Alternative: Концепт 2** — Если команда не готова к 3-4 дням работы, Концепт 2 даёт 80% benefit за 1-2 дня. Но не детектит рестарты между проверками.

**Не рекомендую:** Концепт 3 (недостаточный), Концепт 4 (сложность health-check без net benefit), Концепт 5 (риск откладывания).

## Вердикт

**Статус:** Концепт 1 принят с модификациями.

**Выбор:** Полноценное окно наблюдения с exponential backoff и graceful degradation.

**Обоснование:**
- Закрывает все 10 FR из task.md
- Следует существующим паттернам архитектуры (активность, порт, модель)
- Даёт наблюдаемость через историю Temporal
- Модификации снижают риски нагрузки и unavailable API

**Модификации к original concept:**
1. Exponential backoff вместо фиксированных 10с
2. Graceful degradation при падении `observe()`
3. PID-стабильность = diagnostic, не критерий red status
4. Restart count через косвенный признак (PID change) если API не отдаёт напрямую

**Альтернатива:** Концепт 2 для быстрого win (1-2 дня), но с потерей детекции рестартов.
