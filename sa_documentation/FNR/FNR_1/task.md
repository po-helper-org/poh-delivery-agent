# FNR-1: Окно наблюдения после выкатки

## Описание проблемы

**Текущее поведение:**

Шаг релиза считается успешным сразу после прохождения проверок (`delivery_verify`) в `workflow.py:234-239`. Если проверки зелёные, шаг помечается как выполненный (`workflow.py:243-252`), даже если сервис упадёт через несколько секунд после этого.

**Почему это проблема:**

1. Сервис, который падает через минуту после выкатки, получает статус "зелёный"
2. Поток ошибок, утечка памяти, перезапуск контейнера не обнаруживаются
3. Финальный прогон проверок в первую секунду после выкатки не говорит о поведении системы через минуту
4. Отсутствие наблюдения за состоянием контейнера всё окно

**Следствия:**

- Ложнопозитивная оценка успешности выкатки
- Прод может быть мёртв, хотя релиз показал "зелёный" статус
- Нет возможности обнаружить проблемы, проявляющиеся не мгновенно

## Критерии воспроизведения

**Успешный сценарий:**

1. Релиз доходит до шага выкатки на прод-контур
2. После выкатки проверки проходят успешно
3. Запускается окно наблюдения (120 секунд по умолчанию)
4. Сервис проживает окно, финальные проверки зелёные
5. Шаг помечается как зелёный

**Сбойный сценарий:**

1. Релиз доходит до шага выкатки на прод-контур
2. После выкатки проверки проходят успешно
3. Запускается окно наблюдения
4. Во время окна контейнер останавливается/перезапускается
5. Шаг красный, изменение откачено, очередь остановлена

## Диагностика кодовой базы

### Текущая реализация

**Файл:** `poh_delivery/workflow.py:213-252`

```python
deployed: DeployResult = await workflow.execute_activity(
    "delivery_deploy", args=[repo, merged_sha, bundle.service],
    result_type=DeployResult,
    start_to_close_timeout=timedelta(minutes=15), retry_policy=_WRITE)

checks = []
if deployed.ok:
    checks = await workflow.execute_activity(
        "delivery_verify", args=[bundle.checks, bundle.service],
        result_type=List[CheckResult],
        start_to_close_timeout=timedelta(minutes=10), retry_policy=_READ)

failed = [c for c in checks if not c.ok]
if deployed.ok and not failed:
    # Шаг успешен — БЕЗ окна наблюдения
```

**Проблема:** Между `deploy` и `verify` нет окна наблюдения. Проверки запускаются сразу после выкатки, и сервис прожил даже 1 секунду считается достаточным.

**Проблема:** Нет полей для хранения результатов наблюдения (длительность, статус контейнера, деталь провала).

### Прод-контур

**Файл:** `poh_delivery/prod.py:95-148`

Класс `DockerProd` имеет метод `deploy()`, который:
- Поднимает контейнер из репозитория на нужном SHA
- Ожидает готовности сервиса (`_wait_ready`)
- Возвращает `DeployResult`

**Проблема:** Нет метода для наблюдения за состоянием контейнера во времени.

Метод `report_md()` формирует отчёт релиза. Раздел "Проверки по шагам" (строки 178-187) не содержит информации о наблюдении.

## Границы решения

### Что входит в задачу

1. Окно наблюдения после выкатки КАЖДОГО шага
2. Наблюдение состояния контейнера (запущен ли, не умирал ли, не перезапускался ли)
3. Финальный прогон проверок в конце окна
4. Шаг зелёный только если сервис прожил окно И финальные проверки зелёные
5. Провал в окне = обычный откат (существующая логика)
6. Раздел в отчёте релиза про наблюдение
7. Настраиваемая длительность (умолчание 120с, потолок 15 минут)
8. Ноль = прежнее поведение (для отладки)

### Что НЕ входит в задачу

1. Правила отбора PR — не трогать
2. Ревью-гейт — не трогать
3. Очередь — не трогать
4. Sentry, метрики — у демо-сервиса их нет
5. Отдельное поведение для отката — использовать существующее

## Проверяемые требования

### Функциональные требования

1. **FR-1:** Окно наблюдения запускается после выкатки каждого шага
2. **FR-2:** Длительность окна настраивается через переменную окружения
3. **FR-3:** Умолчание длительности — 120 секунд
4. **FR-4:** Потолок длительности — 900 секунд (15 минут)
5. **FR-5:** Нулевая длительность отключает окно (режим отладки)
6. **FR-6:** Контейнер проверяется на состояние в течение окна
7. **FR-7:** Перезапуск контейнера обнаруживается
8. **FR-8:** Остановка контейнера обнаруживается
9. **FR-9:** Финальные проверки запускаются после окна
10. **FR-10:** Провал окна = откат через существующий механизм

### Нефункциональные требования

1. **NFR-1:** Регрессий — релиз без происшествий проходит как раньше
2. **NFR-2:** Окно не превращает релиз в бесконечное ожидание (потолок)
3. **NFR-3:** Причина отката называет факт, а не жанр
4. **NFR-4:** Решение принимается по доступным индикаторам (без метрик/Sentry)

## Зависимости

Нет внешних зависимостей. Используются только существующие компоненты:
- Docker API для проверки состояния контейнера
- Temporal для деятельности окна
- Существующие механизмы отката

## Риски

1. **Риск 1:** Увеличение времени релиза на 120 секунд на каждый шаг
2. **Риск 2:** Ложные срабатывания при сетевых задержках
3. **Риск 3:** Нет информации о restart count в Docker API без дополнительных вызовов
