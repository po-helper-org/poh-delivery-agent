# poh-delivery-agent

**Delivery-Agent — релиз-менеджер контура производства.**

Миссия и зона ответственности: доставить одобренные PR до прода и проконтролировать,
что система работает ровно так, как описано в БФТ.

Постановка и разбор — [#1](https://github.com/po-helper-org/poh-delivery-agent/issues/1).

## Как это устроено

Отдельный репозиторий, отдельный релизный цикл. В Harness
(`po-helper-org/poh-issue-agents`) подключается **модулем**: пакет ставится в образ
воркера, а сам Harness даёт агенту ровно две вещи — токен GitHub и агента разработки.
Обратной зависимости нет: `poh_delivery` не импортирует из Harness ничего.

```
poh_delivery/
  model.py        факты и решения (dataclass'ы, ездят через Temporal)
  rules.py        КТО едет в релиз и в каком порядке — чистый код, без модели
  render.py       тексты релиза: план до выкатки, отчёт после
  ports.py        протоколы GitHub и прод-контура
  github.py       реализация GitHub-порта поверх REST
  prod.py         прод-контур: выкатка контейнером + проверки живого сервиса
  activities.py   активности Temporal — весь ввод-вывод
  workflow.py     DeliveryRelease: семь шагов от команды до отчёта
  integration.py  точка подключения к Harness
```

Правила очереди считает код, а не модель. По одному снимку состояния план обязан
собираться дважды одинаково — иначе разбор неудачной выкатки упирается в «модель
так решила».

## Что делает

1. Команда `/release` (или метка `run:release`) в наблюдаемом репозитории.
2. Снимает состояние: открытые PR, одобрения, проверки, мержабельность.
3. Конфликтующие ветки отдаёт агенту разработки Harness, потом пересматривает.
4. Строит очередь (дешёвое и независимое — первым), создаёт **черновик релиза** с
   планом, публикует ссылку на него во всех входящих PR.
5. Катит по одному шагу: мерж → выкатка на прод-контур → проверки живого сервиса.
   Провал — `git revert`, возврат прежней сборки, остановка очереди.
6. Дописывает в релиз отчёт: что влито, что изменилось для пользователей, где
   выполнены взаимосвязанные изменения. Публикует релиз.
7. Завершает работу.

## Проверки после выкатки

Что считать «работает как в БФТ», описывает **сам целевой репозиторий** файлом
`.delivery/checks.json`:

```json
{
  "service": { "port": 8080, "start": "node src/server.mjs", "health_path": "/healthz" },
  "checks": [
    { "name": "quote-base", "method": "POST", "path": "/quote",
      "body": { "items": [{ "sku": "a", "price": 1000, "qty": 2 }] },
      "expect_json": { "goods": 2000, "delivery": 300, "total": 2300 },
      "source": "README, раздел «Сервис»" }
  ]
}
```

Нет файла — релиз пойдёт, но в плане будет честно написано, что подтверждать
поведение нечем, кроме факта запуска сервиса.

## Подключение к Harness

```python
# worker.py Harness
from poh_delivery import integration as delivery
import delivery_bridge          # токен GitHub + агент разработки

delivery_bridge.install()
Worker(client, task_queue=delivery.TASK_QUEUE,
       workflows=delivery.WORKFLOWS, activities=delivery.ACTIVITIES, ...)
```

Harness обязан регистрировать активность `delivery_fix_conflicts` на своей очереди —
это агент разработки, которому Delivery-Agent отдаёт конфликтующие ветки.

## Разработка

```bash
pip install -e ".[dev]" pytest-asyncio
pytest -q
```

Тесты воркфлоу поднимают тестовый сервер Temporal и проверяют **порядок внешних
эффектов** — релиз ошибается не в арифметике, а в последовательности.
